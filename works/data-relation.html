S배경 — 데이터는 밖에 넘치는데, 쓸 수가 없다

쓸만한 데이터는 조직 밖에 넘칩니다 — 공공데이터, 통계, 의료, 상용 데이터. 문제는 이 써드파티 데이터를 가져와도 "이게 무슨 데이터고, 우리 데이터와 어떻게 연관되는지"를 파악하는 일부터가 전부 수작업이라는 것. 기존의 정적 메타데이터(스키마·필드명·명세)는 데이터의 특성, 사용 맥락, 시간에 따른 변화를 담지 못해서, 탐색도 연결도 사람의 도메인 지식에 의존합니다.

연결을 자동화하려면, 사람이 연결할 때 쓰던 판단 근거 — 이 필드가 무엇을 의미하는지, 값이 어떤 특성인지 — 가 기계가 읽을 수 있는 형태로 있어야 합니다. 그 정보는 명세서에 없고 데이터 안에 있습니다. 그래서 이 연구는 시스템이 데이터를 분석해 그런 정보를 만들어내는 메타데이터, 즉 액티브 메타데이터를 쌓고, 그걸 근거로 데이터 간 관계 생성을 자동화하는 것을 목표로 합니다.

저는 그중 데이터 의미 이해와 관계 생성, 그리고 통합 카탈로그 축을 맡았습니다.

A설계와 구현 — 수집 → 통합 → 분석 → 관계 생성

Airflow 수집 (4+ 소스) → DCAT 3.0 통합 카탈로그 → AI 컬럼 연관성 분석 → 자동 매핑 · 관계 생성

01이기종 메타데이터 수집 파이프라인

  • Airflow DAG 기반 ETL — 공공데이터포털(Schema.org/DCAT), 국가통계포털, 의료기관 정보, 영화 DB 등 이기종 소스에서 메타데이터를 비동기 수집해 S3(MinIO)에 원본 보존
  • JSON-LD · Schema.org · DCAT · RDF 등 서로 다른 포맷을 수집 단계에서 정규화

02DCAT 3.0 기반 통합 카탈로그

  • 수집된 메타데이터를 국제 표준(DCAT 3.0) 스키마로 통합 — 원본은 JSONB 불변 스냅샷으로 전부 보존해 언제든 역추적 가능
  • Store → Draft → Publish 워크플로우 — AI가 자동 매핑한 결과를 Draft로 만들어 사람이 검토·승인 후 게시, 전 과정을 계보(lineage) 이벤트로 기록
  • 복잡한 중첩 메타데이터를 Key-Value로 평면화해 분석 가능한 형태로 저장, React 기반 워크플로우 UI 제공

03AI 컬럼 연관성 분석 — 시스템의 심장

  • 서로 다른 테이블의 컬럼 간 유사 속성을 Transformer 임베딩(컬럼명·값) + XGBoost 타입 분류 + 코사인 유사도를 결합해 탐지
  • 매칭 전략(다대다 / 1:1 / 유사도순 Greedy)과 임계값 전략을 분리 설계해 정밀도-재현율 트레이드오프를 데이터셋 특성에 맞게 조절
  • 공개 벤치마크 12종으로 성능지표 시험을 설계·수행 — F1 평균 0.87로 과제 KPI(85%) 달성, baseline 대비 최대 +30%p(0.72→0.94) 개선
  • 매칭 결과는 카탈로그의 자동 매핑(Draft 생성)에 직접 연결 — 분석이 분석으로 끝나지 않고 운영 워크플로우를 움직임

04관계 생성 연구 확장

  • GraphSAGE(GNN) 기반 링크 예측 — Schema.org ↔ DCAT처럼 어휘 체계가 다른 메타데이터 간 속성 정렬을 그래프 신경망으로 예측 (실제 공공데이터 50종으로 학습·검증)
  • LLM 기반 관계 생성과 그래프 정규화 POC — 표기가 다른 동일 개체("삼성전자"/"Samsung Electronics")를 정규화 노드로 자동 연결하는 Key-Value 그래프 모델, MCP 연동 Neo4j Cypher 자동 생성
  • DCAT 기반 표준 스키마 매핑 규칙을 문서화·검증해 표준화 작업에 기여

!부딪힌 문제들 — 그리고 어떻게 뚫었나

  • 같은 요청인데 결과가 매번 달랐다. 임베딩용 값 샘플링(20행)이 전역 random 상태에 의존해, 요청 순서에 따라 매칭 결과가 바뀌는 비결정성 버그. 고정 시드의 로컬 RNG로 격리해 동일 요청 = 동일 결과를 보장 — 성능지표 시험 재현성의 전제 조건이었음
  • 과탐(FP)이 지표를 갉아먹었다. 점수 0.8 이상을 수동으로 걸러내던 후처리를 서버측 임계값 파라미터로 승격하고 0.90으로 조정 — movies2 FP 5→1, restaurants3 FP 9→2, 동일 5종 F1 0.784 → 0.926. 임계값 0.70~0.90 스윕으로 모델 점수가 확신/비확신으로 양극화돼 임계값에 둔감함을 검증한 뒤 채택
  • 시험을 쉽게 만들지 않았다. 컬럼명이 동일하게 정렬된 벤치마크 쌍은 전부 만점이 나와 변별력이 없어 제외하고, 컬럼명이 서로 다른(hard) Wikidata 실세계 쌍 등을 편입해 12종으로 확장 — 그 위에서 F1 0.87을 달성했기에 숫자에 방어력이 있음

W기술 선정 이유

Transformer + XGBoost컬럼명·값의 의미(임베딩)와 데이터 타입(분류)은 다른 신호 — 하나로 합치면 놓치는 매칭을 하이브리드로 포착
DCAT 3.0카탈로그 상호운용의 국제 표준 — 자체 스키마 대신 표준을 택해 외부 시스템과의 연계 비용 제거
PostgreSQL JSONB원본 메타데이터를 무손실 보존하면서 표준화 컬럼과 공존 — 매핑이 틀려도 원본에서 재생성 가능
Apache Airflow소스별 수집 주기·실패 격리·재시도를 DAG로 관리
GraphSAGE속성 정렬을 텍스트 유사도만으로 못 푸는 경우(구조적 맥락) 대비 — 그래프 구조 신호를 학습에 결합

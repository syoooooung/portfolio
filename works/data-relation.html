S배경 — 데이터는 밖에 넘치는데, 쓸 수가 없다

쓸만한 데이터는 조직 밖에 넘칩니다 — 공공데이터, 통계, 의료, 상용 데이터. 문제는 이 써드파티 데이터를 가져와도 "이게 무슨 데이터고, 우리 데이터와 어떻게 연관되는지"를 파악하는 일부터가 전부 수작업이라는 것. 기존의 정적 메타데이터(스키마·필드명·명세)는 데이터의 특성, 사용 맥락, 시간에 따른 변화를 담지 못해서, 탐색도 연결도 사람의 도메인 지식에 의존합니다.

연결을 자동화하려면, 사람이 연결할 때 쓰던 판단 근거 — 이 필드가 무엇을 의미하는지, 값이 어떤 특성인지 — 가 기계가 읽을 수 있는 형태로 있어야 합니다. 그 정보는 명세서에 없고 데이터 안에 있습니다. 그래서 이 연구는 시스템이 데이터를 분석해 그런 정보를 만들어내는 메타데이터, 즉 액티브 메타데이터를 쌓고, 그걸 근거로 데이터 간 관계 생성을 자동화하는 것을 목표로 합니다.

저는 그중 데이터 의미 이해와 관계 생성, 그리고 통합 카탈로그 축을 맡았습니다.

A설계와 구현 — 수집 → 통합 → 분석 → 관계 생성

Airflow 수집 (4+ 소스) → DCAT 3.0 통합 카탈로그 → AI 컬럼 연관성 분석 → 자동 매핑 · 관계 생성

01이기종 메타데이터 수집 파이프라인

  • Airflow DAG 기반 ETL — 공공데이터포털(Schema.org/DCAT), 국가통계포털, 의료기관 정보, 영화 DB 등 이기종 소스에서 메타데이터를 비동기 수집해 S3(MinIO)에 원본 보존
  • JSON-LD · Schema.org · DCAT · RDF 등 서로 다른 포맷을 수집 단계에서 정규화

02DCAT 3.0 기반 통합 카탈로그

  • 수집된 메타데이터를 국제 표준(DCAT 3.0) 스키마로 통합 — 원본은 JSONB 불변 스냅샷으로 전부 보존해 언제든 역추적 가능
  • Store → Draft → Publish 워크플로우 — AI가 자동 매핑한 결과를 Draft로 만들어 사람이 검토·승인 후 게시, 전 과정을 계보(lineage) 이벤트로 기록
  • 복잡한 중첩 메타데이터를 Key-Value로 평면화해 분석 가능한 형태로 저장, React 기반 워크플로우 UI 제공

03AI 컬럼 연관성 분석 — 시스템의 심장

  • 서로 다른 테이블의 컬럼 간 유사 속성을 Transformer 임베딩(컬럼명·값) + XGBoost 타입 분류 + 코사인 유사도를 결합해 탐지
  • 매칭 전략(다대다 / 1:1 / 유사도순 Greedy)과 임계값 전략을 분리 설계해 정밀도-재현율 트레이드오프를 데이터셋 특성에 맞게 조절
  • 공개 벤치마크 12종으로 성능지표 시험을 설계·수행 — F1 평균 0.87로 과제 KPI(85%) 달성, baseline 대비 최대 +30%p(0.72→0.94) 개선
  • 매칭 결과는 카탈로그의 자동 매핑(Draft 생성)에 직접 연결 — 분석이 분석으로 끝나지 않고 운영 워크플로우를 움직임

04관계 생성 연구 확장

  • GraphSAGE(GNN) 기반 링크 예측 — Schema.org ↔ DCAT처럼 어휘 체계가 다른 메타데이터 간 속성 정렬을 그래프 신경망으로 예측 (실제 공공데이터 50종으로 학습·검증)
  • LLM 기반 관계 생성과 그래프 정규화 POC — 표기가 다른 동일 개체("삼성전자"/"Samsung Electronics")를 정규화 노드로 자동 연결하는 Key-Value 그래프 모델, MCP 연동 Neo4j Cypher 자동 생성
  • DCAT 기반 표준 스키마 매핑 규칙을 문서화·검증해 표준화 작업에 기여

01

같은 요청인데 결과가 매번 달랐다 — 비결정성 추적

재현성

상황

성능지표 시험을 준비하는데, 같은 데이터셋에 같은 요청을 보내도 매칭 결과가 실행마다 조금씩 달라졌습니다. 공식 시험은 누가 언제 돌려도 같은 수치가 나와야 하는데, 결과가 흔들리면 측정값 자체를 신뢰할 수 없는 상황이었습니다.

해결

호출 경로를 따라 원인을 추적한 결과 — 임베딩용 값 샘플링(테이블당 20행)이 전역 random 상태에 의존해, 앞선 요청이 몇 번 있었는지에 따라 샘플이 달라지는 것을 찾았습니다. 고정 시드의 로컬 RNG로 격리해 요청 순서와 무관하게 동일 요청 = 동일 결과를 보장하고, 동일 요청 반복 실행으로 완전 일치를 확인한 뒤에야 공식 측정을 진행했습니다.

알게 된 점

전역 상태에 기대는 무작위성은 시한폭탄입니다. 그리고 ML 서비스에서 "결과가 이상하다"의 원인이 모델이 아니라 파이프라인의 사소한 비결정성일 수 있다는 것 — 재현성은 성능보다 먼저 확보해야 하는 시험의 전제 조건이라는 것을 배웠습니다.

100%재현성 — 동일 요청 = 동일 결과
반복 실행 완전 일치 확인
20행문제의 샘플링 — 전역 RNG 의존으로
요청 순서에 따라 결과 변동
SEED고정 시드 로컬 RNG로 격리

02

과탐(FP)이 지표를 갉아먹었다 — 임계값을 데이터로 방어

정확도

상황

유사 속성 탐지에서 틀린 매칭(과탐)이 정밀도를 깎았습니다 — movies2에서 FP 5건, restaurants3에서 9건. 게다가 기존에는 점수 0.8 이상만 남기는 수동 후처리에 의존하고 있어서, 시험 절차도 번거롭고 기준도 코드 밖에 있었습니다.

해결

후처리를 서버측 임계값 파라미터로 승격하고 0.90을 채택했습니다. 채택 전에 0.70~0.90 구간을 스윕해 — 모델 점수가 확신/비확신으로 양극화돼 있어 임계값에 둔감함을 확인했습니다. 특정 값에 과적합된 선택이 아니라는 것을 검증한 뒤 고정한 겁니다. 결과는 FP 5→1, 9→2, 동일 5종 F1 0.784 → 0.926.

알게 된 점

하이퍼파라미터 하나도 "왜 그 값인가"를 데이터로 말할 수 있어야 합니다. 민감도 분석(스윕)이 선택의 방어력을 만들고, 기준을 코드 밖 수작업이 아니라 시스템 파라미터로 명시해야 시험이 재현 가능해진다는 것을 배웠습니다.

−78%restaurants3 과탐 — FP 9 → 2
0.93동일 5종 F1 — 0.784 → 0.926

03

시험을 쉽게 만들지 않았다 — 벤치마크 12종 확장 설계

평가 설계

상황

3차년도 성능지표는 벤치마크를 12종으로 확장해 측정해야 했습니다. 그런데 후보 벤치마크 쌍 중 상당수는 두 테이블의 컬럼명이 동일하게 정렬돼 있어 전부 만점 — 시험으로서 변별력이 없었습니다. 쉬운 쌍으로 채우면 숫자는 좋아지지만, 그 숫자는 아무것도 증명하지 못합니다.

해결

만점이 나오는 쌍(컬럼 동일명·도메인 중복) 4종은 공식 셋에서 제외하고 부록의 참고 측정치로만 남겼습니다. 대신 컬럼명이 서로 다르게 명명돼 의미 기반 매칭이 필요한(hard) Wikidata 실세계 쌍 4종과 신규 도메인 쌍 2종을 편입해 12종을 구성했고, 그 위에서 F1 평균 0.8698로 목표(85%)를 달성했습니다.

알게 된 점

지표의 목적은 통과가 아니라 방어입니다. 시험 셋의 난이도 구성이 숫자의 신뢰도를 결정하고, 스스로 어려운 시험을 설계하는 것이 결국 그 결과를 지키는 일이라는 것을 배웠습니다.

12종벤치마크 5 → 12종 확장
hard 실세계 쌍(컬럼명 이질) 편입
−4종만점 나오는 변별력 없는 쌍 제외
부록 참고 측정치로만 수록
0.87확장 12종 F1 평균 — 목표 0.85 달성
